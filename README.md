# Воронка, удержание и A/B-тест: учебный проект по продуктовой аналитике

**За минуту:** проект на синтетических событиях показывает, как построить последовательную воронку, посчитать когортное D1/D7 удержание и проверить заранее спланированный двусторонний A/B-тест. PostgreSQL-запросы сверяются с Python/pandas на тех же данных. Все результаты — симуляция, они не описывают реальный продукт и не доказывают причинный эффект.

## Что сделано и что получилось

- Одна строка назначения — один пользователь эксперимента; события привязаны к устойчивому назначению control/treatment.
- Воронка: landing_view → signup → activation → purchase. Этап должен идти строго после предыдущего в течение 7 суток после назначения.
- Когорты строятся по UTC-дате первой валидной регистрации. D1/D7 — активность на следующий / седьмой календарный день.
- Единственная основная A/B-метрика заранее задана как покупка в течение 7 суток на назначенного пользователя.
- При baseline 12%, MDE +2,4 п.п., α=0,05 и мощности 80% расчёт потребовал 3 119 пользователей на группу. Для симуляции взято 3 200 на группу.
- Результаты фиксированного seed, таблицы воронки и удержания, доверительный интервал, статистический тест и SRM находятся в reports/results.md.

## Данные

Внешние данные не используются: подходящий открытый набор событий с понятными правами для задачи не нужен. Генератор создаёт полностью синтетические назначения и события с фиксированным seed 20261103. В сгенерированном сценарии базовая конверсия в покупку задана равной 12,0%, а для treatment — 14,4%. Это параметры симуляции, а не оценка реального воздействия.

После запуска два CSV создаются в data/generated: таблица назначений и журнал событий. Поля и ограничения описаны в docs/data_dictionary.md. CSV можно пересоздать той же командой; SQL-схема PostgreSQL и загрузка через psql лежат в sql/.

## Методы и ограничения

- В знаменателе каждого этапа воронки — все один раз назначенные пользователи варианта; конверсии считаются по уникальному пользователю.
- Окно воронки и основной метрики: от назначения включительно до назначения +7 суток включительно. Внутренняя последовательность этапов строгая: timestamp следующего события больше предыдущего.
- Когорта — UTC-дата регистрации. D1/D7 — календарный день, а не скользящие интервалы 24/168 часов. D7 считается только для полностью наблюдаемых когорт.
- Для A/B проверяется SRM χ²-тестом при пороге 0,001; основная метрика проверяется двусторонним pooled z-тестом при α=0,05; 95% интервал разности долей строится методом Ньюкомба.
- MDE — плановый порог для расчёта выборки. Статистическая значимость не равна практической ценности.
- Одна симуляция не заменяет тест реального продукта. Здесь нет настоящих пользователей, измерений, инструментов, сезонности или операционных рисков.

Подробный протокол до анализа описан в docs/methodology.md. Короткие корректные формулировки для резюме находятся в resume_phrases.md.

## Запуск

Требуются Python 3.10 или новее, NumPy, pandas и SciPy. Из корня проекта:

~~~powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python scripts/run_analysis.py
python -m unittest discover -s tests -v
~~~

Скрипт создаёт CSV, считает результаты, проверяет SQL/Python-сверку и формирует reports/results.md и reports/results.json. Фиксированный seed делает прогон воспроизводимым. Для повторного анализа уже имеющихся CSV: python scripts/run_analysis.py --reuse-data.

## PostgreSQL

После генерации CSV создайте таблицы и загрузите данные из корня проекта:

~~~powershell
psql $env:DATABASE_URL -f sql/01_schema.sql
psql $env:DATABASE_URL -f sql/05_load.psql
psql $env:DATABASE_URL -f sql/02_funnel.sql
psql $env:DATABASE_URL -f sql/03_retention.sql
psql $env:DATABASE_URL -f sql/04_srm.sql
~~~

Загрузка через psql использует относительные пути из корня проекта. Запросы опираются на UTC epoch/day колонки, чтобы арифметика временных окон была явно определена.

### Сверка SQL и Python на реальном PostgreSQL

Проект проверен на PostgreSQL 16–18: схема создаётся, CSV загружаются, все три запроса исполняются без ошибок, а результаты совпадают с Python до последней строки.

~~~powershell
python scripts/run_analysis.py
psql $env:DATABASE_URL -f sql/01_schema.sql
psql $env:DATABASE_URL -f sql/05_load.psql
python scripts/verify_sql_postgres.py --dsn "host=127.0.0.1 port=5432 user=postgres dbname=postgres"
~~~

Скрипт `scripts/verify_sql_postgres.py` исполняет `sql/02_funnel.sql`, `sql/03_retention.sql` и `sql/04_srm.sql` через `psql`, сравнивает строки воронки, 18 когорт удержания и размеры групп с `reports/results.json`. В GitHub Actions то же самое выполняется в job `postgres` на сервисном контейнере `postgres:16` (`.github/workflows/ci.yml`).

Дополнительно в наборе тестов остаётся быстрая проверка того же SQL-текста в SQLite in-memory — она не заменяет прогон на PostgreSQL, а ловит синтаксические регрессии за секунды.

## Структура

- sql/ — PostgreSQL-схема, воронка, удержание, SRM и загрузка CSV.
- src/analytics_project/ — генератор, аналитика, статистика и сверка с SQL.
- data/generated/ — воспроизводимые синтетические назначения и события.
- tests/ — проверки крайних случаев и SQL/Python parity.
- docs/ — словарь данных и предварительно зафиксированный метод.
- reports/ — результаты конкретного прогона.
